Wake Up, Dev — anexo técnico del TFM

El sistema operativo
detrás del juego

Este TFM no se construyó en un editor suelto: se construyó dentro de un Second Brain — una bóveda de conocimiento que funciona como sistema operativo de desarrollo, donde los agentes de IA leen el contexto, ejecutan el trabajo y dejan rastro. La bóveda es privada (contiene proyectos personales); esta página documenta su diseño, stack y patrones, que son la parte transferible.

> ¿Qué es?

Una carpeta de Markdown versionada con Git y visualizada con Obsidian. Nada más — y eso es deliberado: texto plano que cualquier agente puede leer y escribir sin SDK, con historial completo gratis y sincronización multi-PC vía GitHub. Sobre esa base se montan tres roles a la vez:

Base de conocimiento

Notas del máster, prompts, plantillas, decisiones con su porqué. Lo que la IA necesita para trabajar con contexto real.

Interfaz de agentes

Los agentes (Claude Code, Copilot CLI, Codex) operan DENTRO de la bóveda: leen el contexto del proyecto y escriben journal, issues y aprendizajes.

Registro de trabajo

Issues, journal diario y ledger de delegaciones. El proceso queda auditable — parte de lo que se entrega en este TFM es el proceso.

Anatomía (clic en cada capa)

00_SYSTEM Conocimiento reutilizable ▸

Skills (procedimientos invocables), plantillas de proyecto y prompts compartidos. Es la parte que no pertenece a ningún proyecto: el "userland" que cualquier agente carga bajo demanda.

01_PROJECTS Un mini-OS por proyecto ▸

Cada proyecto lleva su contexto para IA (ai-context/), issues, journal, aprendizajes propios y una carpeta code/ que es un repo Git independiente — la bóveda versiona el conocimiento, el código se versiona aparte. Wake Up, Dev vive así: su repo público cuelga de un proyecto privado.

02_JOURNAL Capa de ejecución ▸

Journal global diario + notificaciones que los agentes se dejan entre sí (una instancia termina → deja una nota → el heartbeat la procesa al día siguiente).

03_RESOURCES Destilados consultables ▸

Cápsulas de conocimiento extraídas de las notas largas — p. ej. las ~300 notas del máster destiladas para que cualquier otro proyecto las consulte sin cargarlas enteras.

04_META El sistema sobre sí mismo ▸

Workflows, el motor de loops y los aprendizajes: reglas de cómo trabajar, un archivo por regla, con índice que se carga en cada sesión. Acá vive el bucle de auto-mejora.

> Stack e infraestructura

DATOS

Markdown + Git

La "base de datos" es texto plano con frontmatter YAML. GitHub como único mecanismo de sync entre máquinas — sin servicios de pago, sin lock-in.

RUNTIME

CLIs de agentes

Claude Code como coordinador; instancias headless de Copilot CLI / Codex como ejecutoras. Cada CLI arranca en la bóveda y hereda el contexto del proyecto.

UI

Dashboard local

App web local (Vite + React) que expone la bóveda como API JSON: cola de delegaciones en vivo, loops programados, issues, journal. Solo escucha en localhost.

PUENTE

Servidor MCP propio

El corazón: un servidor Model Context Protocol que expone ~50 herramientas sb_* para que cualquier agente opere el sistema por contrato, no por convención.

terminal — un día de trabajo típico
# el humano define QUÉ; el coordinador reparte; los writers ejecutan
> sb_overview            # estado global: proyectos, issues, loops
> sb_issues --actionable  # qué está listo para implementar
> sb_delegate { project, prompt, cli: "copilot", scope: [...] }
                        # lanza un writer headless en su worktree
> sb_task_output id      # el coordinador recoge el reporte y verifica
> sb_journal             # el día queda escrito solo

> Delegación multiagente

La regla operativa: el coordinador no escribe código — clasifica, especifica y delega; los writers implementan; los reportes se verifican contra el repo real (una hija puede afirmar cualquier cosa: la evidencia se contrasta, no se cree). Así se corrigieron, por ejemplo, los bancos de retos de este juego: una revisión E2E produjo el informe-spec, y dos writers Copilot aplicaron 61 correcciones en paralelo con scopes disjuntos.

1SpecAnálisis previo tipo SDD: un informe con ítems concretos y criterios verificables. Sin spec no hay delegación de tareas medianas o grandes.
2sb_delegateCada writer nace headless en un git worktree propio (rama task/<id>), con un scope declarado de archivos: scopes disjuntos = paralelismo seguro.
3GatesEl writer corre typecheck y tests en su worktree y commitea en su rama. Nunca toca main.
4VerificaciónEl coordinador comprueba que el commit EXISTE en el repo, hace spot-checks del contenido y recién entonces mergea.
Familia de toolsEjemplosPara qué
Trabajosb_delegate, sb_queue, sb_task_output, sb_leasesDelegar, ver la cola, recoger reportes, respetar la capacidad de la máquina (tope de writers y RAM)
Conocimientosb_search, sb_ask, sb_learnings, sb_read_docConsultar la bóveda sin cargarla entera en contexto

Los loops cierran el círculo: un heartbeat lee el estado cada mañana y genera un briefing; un auto-scan detecta issues listos y propone la cascada; un loop de auto-mejora cruza los aprendizajes con las métricas y abre issues sobre el propio sistema. El humano queda como gate de decisión, no como cuello de botella de ejecución.

> El patrón de skills

Una skill es un procedimiento en Markdown que el agente carga al invocarla — la versión operativa de "cómo hacemos esto acá". La bóveda tiene decenas (orquestación, debugging con análisis de causa raíz, journaling, transcripción de reuniones). La más ilustrativa es la que convierte feedback en reglas permanentes:

skill: registrar-aprendizaje
# El usuario corrige algo por segunda vez → eso es una regla, no un chat
1. Se escribe 04_META/aprendizajes/<slug>.md — un archivo POR regla:
     qué pasó, por qué importa, y cómo aplicarla la próxima vez.
2. Se agrega una línea al índice, que se carga en cada sesión nueva.
3. El agente siguiente arranca sabiendo lo que a este le costó aprender.

# Ejemplo real (de esta misma semana, sanitizado):
ruteo-coordinador.md — "Claude coordina y delega la implementación a
  writers Copilot para economizar tokens; el modelo grande escribe solo
  en tareas de gráfica compleja; toda tarea mediana o grande lleva una
  spec previa. Why: el usuario lo pidió tres veces en una sesión."

El efecto compuesto es el punto: los errores se pagan una vez. La lista de "bugs ya pagados" del propio juego funciona igual — el AGENTS.md del repo es la versión pública del patrón: reglas de arquitectura y gotchas que cada agente lee antes de tocar código.

> Caso aplicado: el Oráculo

En el juego, la IA no es solo herramienta de construcción: es mecánica. El Oráculo responde dudas, un evaluador califica respuestas abiertas contra rúbrica y hay pistas generadas. Todo eso es un personaje moldeado por system prompts sobre una capa de adapters intercambiables (Anthropic / OpenAI / Gemini / bridge local), BYOK y con fallback estático: el juego entero funciona sin ninguna API key.

src/ai/prompts.ts — systemOraculo (literal, del repo público)
"Sos el Oráculo del juego educativo 'Wake Up, Dev', ambientado en Matrix.
El jugador es un estudiante del Máster en Desarrollo con IA repasando un módulo.
Respondé sus dudas sobre el contenido del módulo de forma didáctica, en español,
en 120 palabras o menos. Usá analogías simples cuando ayuden.
Nunca des la respuesta literal de un reto del juego: guiá para que la deduzca.
Mantené un tono sereno y levemente enigmático, como el Oráculo de Matrix,
pero priorizá siempre la claridad didáctica sobre el personaje."

+ contexto del módulo actual (el campo modulo.resumen del banco JSON)

Por qué funciona

Las dos líneas en ámbar son las que hacen al personaje jugable: la primera protege la mecánica (no regalar respuestas), la segunda subordina el disfraz a la didáctica. El resto es tono.

El mismo patrón, tres roles

systemEvaluador exige JSON estricto y criterio justo ("no exijas terminología exacta si el concepto está bien"); systemPista limita a 30 palabras sin descartar opciones. Cada rol es un contrato de prompt, testeado con adapters mockeados.

> En números

10 niveles

Uno por módulo del máster, cada uno con su escenario pixel-art y su banco de retos.

312 retos

Generados desde las notas reales del curso con un pipeline documentado, revisados E2E con una spec de 67 correcciones aplicada por writers en paralelo.

140+ tests

Dominio puro y adapters mockeados; CI + deploy automático a GitHub Pages en cada push. El backlog del juego es público: compartir el proceso es parte de la entrega.

La bóveda en sí no se publica: contiene proyectos personales y de trabajo. Lo compartible es esto — la arquitectura, el stack y los patrones — más todo el repo del juego, cuyo desarrollo completo (issues, auditorías multiagente, decisiones) sí es público.
